# dsh-kite — 对标 ZCode 的增量设计（v0.2）

> 输入：`DSH-手机远程访问插件-完整方案-2026-09-30.md`（下称「方案」）+ `dsh-kite`（原名 dsh-remote-access，2026-10 更名）v0.1.0 实现

## 0. 结论

**该抄 6 条，已超越 3 条，明确不抄 3 条。**

其中只有 **2 条是真正的缺口**（会在移动网络下真实翻车），其余是低成本体验/可观测性收益：

| 优先级 | 增量 | 为什么必须做 |
| --- | --- | --- |
| **P0** | 承载层帧 ACK + 重传 + 续传窗口 | 手机切后台/地铁断网 → WS 半开 → **帧静默丢失，前端表现为"卡住"**。现在没有帧级确认，丢了不知道 |
| **P0** | 应用层心跳（ACK 时间）替代 socket 存活判定 | 现有 `ping/pong` 只证 socket 活。半开连接上 socket 是"活的"，但对端已经不处理了 |
| P1 | 单终端约束 + `KICKED`/conflict 语义 | 同一设备开两个页面 → 各自拿一个 ticket → 行为不确定（谁的请求算谁的） |
| P1 | 配对票据的**目标绑定**（workspace/session 范围） | 现在配对链接是"全量通行证"；ZCode 绑到具体工作区 |
| P2 | 手机端诊断上报（`visibilityState`/`hiddenDurationMs`/close 详情） | 移动端排障的唯一数据来源；现在只有 `ra.disconnect.reason` 一个 counter |
| P2 | 二维码渲染 | 纯体验：少一步复制粘贴 |
| — | 凭据失效**单向自愈**（只重试一次） | 低成本防死循环，顺手抄 |

## 2. P0 增量：承载层可靠性

### 2.1 问题陈述（先证明缺口真实存在）

现在的链路：手机 WS → 中继 → Connector → 回环 Host。任何一段的帧丢失都是**静默**的：

```js
// transport/frames.js 现状（节选）
http-body    {deviceId,streamId,chunk(b64),final}      phone→conn
http-res-body{deviceId,streamId,chunk(b64),final}      conn→phone
ws-data      {deviceId,streamId,fin,opcode,data(b64)}  双向
```

- `final` / `fin` 是**结束标记**，不是**确认标记**。
- 分片之间没有序号：丢了中间一片，接收侧只能等 `final` 超时（或永久等下去）。
- 中继有"30s 响应看门狗"，但它看的是**请求有没有响应**，不是**每一帧有没有到达**。
- 手机切后台：iOS/Android 都会冻结或丢弃 WebSocket。回来的连接是"新的"，旧流上的分片永远补不回来。

**ZCode 的做法**：给每一帧 `seq`（物理）与 `messageSeq`（逻辑），接收侧按 `messageSeq` 回 `rpc-frame-ack`，发送侧用双指针窗口推进；未确认的留在 8 MiB / 45s 的重放缓冲里，socket 换新时重放。丢帧时量化上报（`bridge-degraded{reason:'rpc-frame-gap', expectedSeq, droppedCount}`）。

### 2.2 协议增量：承载帧加三层元数据

在**不改变语义层**（DSH 的 `/api/*` 与 `/api/remote.mux` 仍然复用）的前提下，只给信封加字段：

```js
// transport/frames.js — v0.2 帧信封（exactKeys 纪律不变，多余字段仍一律拒绝）
//
// 新增通用尾部字段（所有 phone↔conn 的数据帧都可带）：
//   gen   : number  连接代际（Connector 每次重启/换 relay 递增；见 §2.4）
//   seq   : number  物理帧序号（per stream，单调 +1）
//   mseq  : number  逻辑消息序号（分片归属；同一消息的所有分片 mseq 相同）
//   fidx  : number  分片下标（0-based）
//   fcnt  : number  分片总数
//   mb    : number  逻辑消息总字节（校验用）
//   crc   : string  crc32 十六进制（8 位小写，对 chunk 的**原始字节**计算）
//
// 新增控制帧：
//   ack   {gen,deviceId,streamId,mseq}                      确认收到某逻辑消息
//   resume{gen,deviceId,streamId,fromSeq}                   请求从 fromSeq 起重放
//   gap   {gen,deviceId,streamId,expectedSeq,dropped,reason} 量化丢帧上报
//
// ping 升级（现在是空帧）：
//   ping  {gen,ts,ackedSeq}       ts = Date.now()，ackedSeq = 本侧已连续确认到的 seq
//   pong  {gen,ts,echoTs}         echoTs 原样回传，用于算 RTT
```

**五条不变量（必须写进契约测试）**：

1. `fidx < fcnt`；`fcnt <= mb`（非空分片数不可能超过总字节数）—— 直接沿用 ZCode 的 `superRefine`。
2. 同一逻辑消息的所有分片 `mseq` 相同、`fidx` 覆盖 `[0, fcnt)` 无缺无重。
3. `crc32(chunk)` 必须等于 `crc`；不等则该分片丢弃并按 4 处理。
4. 收到 `seq` 不连续时**不下发**，先发 `gap{expectedSeq, dropped}`，然后发 `resume{fromSeq: expectedSeq}`。
5. 未知 `kind` 仍是协议错误（断连）；但**未知的尾部字段**必须拒绝（`exactKeys` 不变）——不要为了前向兼容放宽这条。

> **为什么 crc 加在承载层**：中继只转发不解密，它在 TLS 层有完整性；但 Connector 侧读回环、手机侧读 IndexedDB 后的重组都在应用层。crc32 很便宜，能区分"中继把帧拼错了"和"对端没收到"。

### 2.3 双指针窗口（照 ZCode 的结构，参数按 DSH 场景调）

```js
// transport/ack-window.js（新增）
class AckWindow {
  #buf = [];          // 未确认的 {seq, mseq, bytes, frame}
  #head = 0;          // 最早未确认
  #nextUnsent = 0;    // 下一个待发

  get activeCount()          { return this.#buf.length - this.#head; }
  get retainedPayloadBytes() { /* 累加 bytes，喂饱和水位 */ }

  append(frame) { ... }
  ackUpTo(mseq) { /* head 前进，回收 */ }
  unsentBatch(maxBytes) { /* 从 nextUnsent 取一批 ≤ maxBytes */ }
  replayFrom(seq) { /* resume 用：返回 seq 之后的全部未确认帧 */ }
}
```

| 参数 | ZCode 取值 | 本方案建议 | 理由 |
| --- | --- | --- | --- |
| 重放缓冲上限 | 8 MiB | **4 MiB** | 手机侧内存更紧；DSH 的响应体本就分片传输 |
| 重放宽限窗 | 45s | **45s（照抄）** | 手机切后台-回来的典型间隔就在这个量级 |
| 饱和高水位 | 1 MiB | **1 MiB（照抄）** | 与 `MAX_FRAME_BYTES` 同量级，合理 |
| 饱和低水位 | 256 KiB | **256 KiB（照抄）** | 与 `MAX_CHUNK_BYTES` 一致 |
| 分片上限 | 64 | **64（照抄）** | 64 × 256 KiB = 16 MiB 单消息上限，够用 |
| 装配超时 | 30s | **30s（照抄）** | 与中继响应看门狗同值，避免两套超时打架 |

**饱和信号要透传到 DSH 侧**：ZCode 是 `onSaturated/onDrained → hostProtocol.sendFlowState('saturated'|'drained')`，让拥塞反压到产出方。本方案对应的是：Connector 在 relay 侧饱和时，**降低对回环 Host 的读取速率**（而不是继续读、堆在内存里）。这是唯一能防"手机在地铁里，本机内存被响应体吃爆"的手段。

### 2.4 `gen`（连接代际）——为什么需要它

ZCode 用 `bridgeSessionId + bridgeGeneration + recoveryId` 三者全等来拒绝跨代际的残留帧。本方案只需要一个简化的 `gen`：

- Connector 每次启动 / 换 `relayUrl` / 换 `relayToken` → `gen += 1`（持久化）。
- 手机在 `auth-result` 里拿到 `gen`。
- 所有数据帧带 `gen`；`gen` 不匹配的帧**直接丢弃并计入 `gap.reason='stale-gen'`**。
- 目的：Connector 重启后，旧连接上残留的帧不会被当成本次会话的数据。

**成本极低（一个持久化整数 + 一处比较），但能消掉一整类"重启后偶发错帧"的诡异 bug。**

### 2.5 应用层心跳：从"socket 活"升级到"对端在处理"

```js
// 现状：空 ping/pong，只能证明 TCP/WS 没断
// v0.2：
//   每 15s： send({ kind:'ping', gen, ts:Date.now(), ackedSeq: myWin.lastContiguousAcked })
//   收到：   send({ kind:'pong', gen, ts:Date.now(), echoTs: frame.ts })
//   收到 pong： rtt = now - echoTs；lastAckAt = now
//   30s 无 pong → 判 stale → 主动 close + resume 重连（不是等 socket close）
```

**关键点（ZCode 的原话是「stale 检测靠应用层 ACK 时间」）**：
- 判定 stale 用的是**收到 `pong` 的时间**，不是 `socket.readyState`。
- 半开连接（对端进程 hang / 中继转发卡住）在 socket 层面是"连着的"——只有应用层心跳能发现。
- 30s 这个值要**大于** `ping` 间隔的 2 倍，且**等于** ZCode 的 watchdog 值（便于对照排障）。

**重连后必须 `resume` 而不是重建**：`resume{fromSeq}` 让 Connector 从重放缓冲里补帧；缓冲已过期（>45s）才退化为"让前端重新拉快照"（对齐方案 §10.3 的 `asOfSeq` 策略）。

## 3. P1 增量：单终端约束与配对目标绑定

### 3.1 单终端约束（`KICKED` / conflict）

**现状缺口**：`kick{deviceId}` 是按设备踢的，一个设备可以开 N 个页面，每个页面各自持 ticket、各自发请求。`streamId` 是 per-stream 的，所以不会串数据；但会出现：
- 两个页面同时发 `session/prompt` → 两条用户消息（这不是 bug，但用户以为是 bug）；
- 一个页面在做长流式响应，另一个页面刷新 → 旧页面的流没人回收。

**ZCode 的做法**：`singlePageNote`「当前 relay 配对同一时间只支持一个手机页面；如果已经在别的页面打开，请先关闭旧页面」，冲突走 `KICKED` → `session-conflict`。

**本方案建议（比 ZCode 更细一点）**：

```js
// 新增帧
presence { gen, deviceId, pageId, ts }        phone→conn  页面心跳/声明
presence-ack { gen, deviceId, pageId, role }  conn→phone  role: 'active' | 'observer'
kick-page { gen, deviceId, pageId, reason }   conn→phone  reason: 'superseded' | 'revoked'
```

- Connector 为每个 `deviceId` 维护**一个 active pageId**（LRU）。
- 新页面 claim 成功 → 旧页面收 `kick-page{reason:'superseded'}` → 前端提示「已在其他页面打开」并降级为只读或退出。
- **提供 `observer` 角色**（可选，M2 再做）：只读页面不抢 active，用于"平板上看进展，手机上操作"——这是 ZCode 没做的、但对 DSH 用户明显有价值的一点（他们常常同时开着多个设备）。

> **与 ZCode 的差异是有意的**：ZCode 一刀切单页面；DSH 场景下"多设备看同一个任务"是真实需求，所以设计成 `active` + `observer` 两种角色，默认单 active。

### 3.2 配对票据的目标绑定

**现状**：`pair-result{...,deviceId,code,setCookie}` 之后设备就拿到了 ticket，可以访问**全部** `/api/*`。

**ZCode 的做法**：`authorizeStart(windowId, workspace)` 生成 `{token, expiresAt, windowId, workspaceKey, remoteSessionId}`，`consumeStartAuthorization` 校验票据全等 + 未过期（**先删后校验**）。

**本方案建议**：配对链接增加 scope，且 scope 进入 ticket 与 ACL：

```js
// pairing.js 生成 token 时带上 scope
pairToken = { token, expiresAt, scope }
scope = {
  kind: 'all' | 'workspaces',
  workspaceKeys?: string[],   // kind='workspaces' 时的白名单
  allowTerminal: bool,        // 覆盖全局配置（默认继承 cordis.patch.yml）
  allowUpload: bool,
}

// ticket 校验时叠加 scope 检查（policy/ 层，不是代理层）
if (scope.kind === 'workspaces' && !scope.workspaceKeys.includes(reqWorkspaceKey)) → 403 ra.scope.denied
```

**收益**：可以发一个"只能看 qait-web 这个工作区、不能开终端"的链接给同事，而不用把整台机器交出去。
**成本**：`identity/pairing.js` + `policy/` 各加一处检查；`admin/panel.js` 生成链接时多两个选择项。

> 这一条是**产品能力**而不只是安全加固——它让"临时给别人看一下"成为可能。ZCode 用它绑工作区，我们绑工作区 + 能力子集。

## 4. P2 增量：可观测性与体验

### 4.1 手机端诊断上报（照 ZCode 的字段，去掉不适用的）

```js
diag { gen, deviceId, event, ts, ... }
event ∈ {
  'state-transition',   // + state, previousState
  'socket-close',       // + closeCode, closeReason, wasClean, wasPaired
  'socket-error',
  'recover-start', 'recover-scheduled',
  'visibility',         // + visibilityState, hiddenDurationMs   ← 新增，ZCode 有
  'online',             // + online
  'resume-result',      // + ok, replayedFrames, gapCount        ← 本方案新增
}
```

**为什么 `visibility` + `hiddenDurationMs` 是最有价值的一条**：移动端"卡住"的根因绝大多数是"页面被切到后台 → socket 被冻结 → 回来时流已经断了"。没有这个字段，你在日志里只能看到"连接断了"，永远不知道是网络问题还是后台冻结。有了它，`hiddenDurationMs` 直接指认。

`resume-result{ok, replayedFrames, gapCount}` 是本方案额外加的——它把 §2 的重放效果变成**可观测的数字**，直接喂给指标（见 §6）。

### 4.2 二维码渲染

- 桌面面板 `admin/panel.js`：把配对链接渲染成二维码（图片或 SVG）。
- **零依赖做法**：服务端用 `Buffer` 手写 QR 太麻烦；更省的是**面板里引一个 3KB 的 qrcode 实现**，或者干脆用 `data:` URL + 前端 canvas。
- 判定：**纯体验增量，不引入新依赖优先**。如果必须引依赖，放进 `relay/` 那个"唯一允许依赖 ws"的纪律之外——也就是说，**面板侧允许引，Connector 与 relay 不允许**。

### 4.3 凭据失效单向自愈

```js
// auth 失败时：
if (ticketInvalid && !this.#invalidTicketRetryUsed) {
  this.#invalidTicketRetryUsed = true;
  await this.#clearLocalTicket();      // 清本地票据，保留设备私钥
  this.#reconnect({ mode: 'reauth' });  // 走一次挑战-应答，不要求重新扫码
  return;
}
// 第二次仍失败 → 明确报错给用户（"设备已被撤销或被中继拒绝"），不再自动重试
```

**要点**：只自愈**一次**（ZCode 的 `invalidPersistedRetryUsed`），且自愈的是**票据**不是**设备私钥**——私钥清掉就得重新扫码，那是最后手段。

## 5. 明确不抄的三条（附理由）

| ZCode 机制 | 为什么不抄 |
| --- | --- |
| **工作区桥**（`attachWorkspaceHost` + `MessageChannelMain` + `entryId`） | 它是为"手机要挂到桌面的 Host 会话上"设计的。本方案的 Connector 直接复用同一个 WebServer 与同一套 cookie，**根本不存在"挂载"这一步**——架构上已经绕过了它要解决的问题。抄它只会平白多一层。 |
| **`mobileViewState` 视图优先级** | ZCode 的桌面与手机共享同一个工作区会话（`activeWorkspaceKey`/`activeTaskId` 是一份状态），所以必须解决"谁说了算"。本方案里手机是**独立客户端**，各自维护自己的视图，不存在抢占。 |
| **列表推送签名去重**（`workspace-list-updated` 的规范化签名） | 那是**应用层**的推送优化，属于 DSH 前端职责。承载层（Connector）是透明代理，不该知道"什么变了"。加在这里会违反方案的"承载层不解释语义"原则。 |

## 6. 分期与关门阈值（对齐方案 §12/§13）

**不新增里程碑**，把增量塞进现有 M2/M3：

| 里程碑 | 原有交付 | **新增（本文）** | 关门阈值（新增部分） |

| M2 收敛 | 策略层 + 移动优化页 | **P0：帧 ACK/重传/窗口 + `gen` + 应用层心跳**<br>**P0：`gap` 量化 + 饱和反压** | 模拟弱网（Chrome DevTools 的 offline 30s / 3G）下：<br>① 页面恢复后**无丢失消息**；<br>② `ra.resume.replayed` > 0 且 `ra.gap.count` 有值可观测；<br>③ 本机内存不因缓冲超 200 MiB |

## 8. 需要写的 ADR（补记）

沿用方案 §3 的 ADR 编号（已有 001–005）：

**ADR-006：承载层引入帧级 ACK 与有限重放，而不是依赖 WS 的有序可靠**
理由：WS 保证的是"连接存续期间的有序可靠"，不保证"断连恢复后不丢"。手机切后台会换 socket。ZCode 在真实移动网络下做了同样的选择。
代价：Connector 与手机侧各需一个窗口实现 + 内存上限；必须给重放加"只重放未确认"的硬约束，否则会重复投递。

**ADR-007：重放缓冲 4 MiB / 45s，超期退化为应用层快照**
理由：手机侧内存比桌面紧；45s 覆盖绝大多数后台切换。超期时不在承载层硬扛，而是交给方案 §10.3 的 `asOfSeq` 快照+增量。
代价：需要前端配合"重放失败 → 重新拉快照"的分支。

**ADR-008：单终端默认 active + 可选 observer，而非 ZCode 的一刀切单页面**
理由：DSH 用户真实场景是"手机操作 + 平板看"，一刀切会逼用户关页面。
代价：Connector 需要维护 per-device 的 pageId 角色表；写请求必须校验 active。

**ADR-009：配对票据引入 scope（工作区 + 能力子集）**
理由：现在一个配对链接等于交出整机；引入 scope 后可以发"只读某工作区"的链接。
代价：`policy/` 与 `proxy/` 都要能拿到 `workspaceKey`——需要确认 DSH 的请求里哪个字段可靠地携带它（**待探针验证**，见 §9）。

## 9. 开工前必须先验证的三件事（对齐方案 §8.5「探针先行」）

1. **`workspaceKey` 在代理层是否可得**：ADR-009 依赖它。如果 DSH 的 `/api/*` 请求里不携带可解析的工作区标识（只在 body 里、且在 `/api/remote.mux` 的语义帧内），那 scope 就只能按"会话 id"而不是"工作区"绑，或退化为能力子集（终端/上传开关）——**这会让 ADR-009 缩水，但不应因此放弃**。
2. **`/api/remote.mux` 的帧流是否有可用的序号**：§2 的 `seq` 是承载层自己发的，与 DSH 无关，所以这条不阻塞 P0；但如果 DSH 的 mux 帧本身有 `asOfSeq` 之类的游标，应用层续传会更精确（方案 §10.3 已假设有）。
3. **手机端能否稳定拿到 `visibilitychange`**：iOS Safari 对 PWA 的后台事件有延迟/丢失的已知问题。如果拿不到，`hiddenDurationMs` 要退化为"两次 ping 之间的间隔"估算——**先测，再决定字段语义**。

---

## 10. 一句话总结

现有方案缺的不是架构，是 **ZCode 用真实移动网络踩出来的那几层"丢了怎么办"的机制**。
P0 只有两条（帧级 ACK/重放、应用层心跳），都在承载层，不碰语义层，不动现有架构；
P1/P2 各两条，都是低成本项。
**先做 P0 并用指标证明"重放真的发生过"——证明不了就停下，不要继续搬。**
