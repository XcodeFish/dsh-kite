## 一、终审判定

**三份报告的核心论断全部成立，无一条被代码推翻。** 架构与信任链（一次性配对令牌、Ed25519 挑战应答、白名单重建头、策略黑名单、审计、kill switch 文件持久化）设计扎实；但实现层存在一个结构性根因和一组配套缺口，其中 P0 级问题在 146 项全绿测试下可稳定复现利用。

1. **根因只有一个**：请求目标被解析两次——策略判定看原始字符串（`policy.decide(raw)` + `safeProxyPath(raw)`），实际发送用 `new URL(raw, base)` 归一化后的结果。两次解析之间的映射差异（点段折叠、authority 切换、`%2e` 编码）构成全部 Critical 绕过面。
2. **推荐修复已实测，不是纸面代码**：方案 §1 的 `canonicalizeTarget` 原样运行——恶意写法 **9/9 拦下**（含 `/./`、`/x/../`、`/%2e/`、`//evil.example/x`、`/kite%2Fapi%2Fstatus`）、正常流量 **10/10 无回归**（含 `/plugins/??a.js,b.js&rev=x` 合并模块、query 含 `%2E/%2F` 的 attachment）、不变式 `pathname+search === key` 逐字节成立。
3. **方案落地状态：0/4**。`canonicalizeTarget`、`VIA_HEADER` 全仓库 grep 0 命中；146 项测试全部通过（本次实跑 146/146），而绕过就在绿测试下成立——因为现有断言只用规范写法，"同一语义的另一种写法"这一维度整体缺失。

## 三、对报告三的措辞修正（不改变结论，改变执行精度）

1. **"relay 路由表任意客户端可改"已部分过时**：`devices` 上报在 2026-10-02 已加所有权保护（他连接器名下设备拒绝抢注，`relay/server.mjs:749-765`，真机事故修复）。**但 `kick`（`relay/server.mjs:763-770`）仍无归属校验**——任何连接器可踢除任意 deviceId。P2#1 的范围从"devices/kick 双修"缩小为"kick 补归属校验"。
2. **"kill switch 只写文件、完全不生效"过强**：`isKilled` 已接入连接器的 `start()` 与 `#connect()`——kill 后**新建与重连被阻止**。真实缺口是：面板切换不 `dispose()` 在途隧道、`#handleHttp` 无逐请求复检。即"阻止未来连接成立、立即断开既有连接不成立"。方案 §5 的修法（toggle 回调 dispose/重建 + `#handleHttp` 复检）仍然正确且必要。
3. **`authChallenges`"只增不清"不准**：完成的条目会删（`transport/relay-client.js:506-507`）；无淘汰的是**被弃条目**（auth-begin 后未完成）。缺的是 sweep，不是全部清理。
4. **测试基线**：报告三写 145/146（二进制帧用例超时），本次实跑 **146/146 全绿**。不影响任何结论——绿测试与可利用并存恰恰是本报告的核心论据。

## 七、兼容性影响评估（方案会不会影响正常使用）

### P0（§1–§4）：对正常使用零感知

- 良性流量矩阵实测 10/10 放行：`/plugins/??a,b&rev=x` 合并模块、query 含 `%2E/%2F` 的 attachment、`/api/remote.mux`、`terminal/follow`、`%20` 空格、长路径全部不受影响；query 完全不检查（只查 pathname）。
- WS 同门（§3）只新增拒绝「HTTP 侧本来就拒」的路径：手机 PWA 主通道 `/api/remote.mux` 是未知路径→放行、`terminal/follow` 在 `TERMINAL_READ` 白名单；`/plugins/events`（HMR）在远程本就无意义且 HTTP 侧已被拒。无功能损失。
- 出站组装（§2）与来源标记头（§4）对手机完全透明。

### P1（§5–§8）：两处需要按修正执行，否则有真实影响

1. **限流阈值直接照抄会打断 PWA 首次加载**：部署形态是 Caddy 回环反代，所有手机 HTTP 共享 `remoteAddress=127.0.0.1` 一个桶；首次加载即 57+ 个客户端模块请求，60/min 全局桶会打出 429。修正：**严格限流只上 `/connector` 升级与配对端点**（60/min 足够），手机 HTTP 用高阈值独立桶（建议 ≥600/min）或仅做异常熔断；采信回环来源的 XFF 按方案执行。
2. **中继 fail-closed 是一次运维迁移而非故障**：现网若正以 OPEN（无 RELAY_TOKENS）运行，升级后中继拒绝启动、手机断连——这是预期行为，但需在 DEPLOY/README 写明迁移步骤（先配 token 再重启；本机联调 `ALLOW_OPEN=1`）。
3. 引导令牌 10 分钟：面板是内联进 DSH 主页面 DOM 渲染的（panel-client 走父上下文 fetch），打开时现取 `/kite/api/entry`，正常使用无感；最坏情形（DSH 页面挂 >10 分钟后点开面板）由宿主会话轨兜底，代价仅为刷新一次 DSH 页面。kill switch 真断线（§5）恢复的是文档承诺的行为本身，属修复而非影响。

### P2：一处执行顺序问题

- **CSP `default-src 'self'` 会直接打死管理面**：`admin/panel.js` 有 2 处内联 `<script>` 和内联 `onclick`（panel.js:513,576）。必须与「移除 onclick 拼接」同一批做，或 CSP 先放行 `script-src 'self' 'unsafe-inline'`（仅此页），再逐步收紧。其余 P2 项（deflate 关上下文接管——手机浏览器标准支持、原子写、sweep、幽灵设备、kick 归属校验）对正常使用无感或仅增 CPU 微开销。

**结论：方案整体可安全落地。P0 直接按 §11 执行即可；P1 按上述两点修正执行；P2 的 CSP 项调整顺序。**
