## 修复复核附录（2026-10-03）

### 已关闭的 P0/P1 风险

- Connector replacement close 现在只允许当前 socket 清理路由和流，旧 socket 不会删除新连接设备表。
- HTTP stream 绑定真实 `connectorId`，跨 connector 断开不再误杀；已发送响应头时不会二次 `writeHead`。

- Connector 发送端增加 `bufferedAmount` 上限和 hello-ack watchdog；旧代际 stream 不再向新 socket 发送。

## 四、问题清单

## P0-1：同 connectorId 替换会删除新连接路由

**影响：重连成功但设备路由消失，手机随后 401/503 或实时通道 4503。**

`relay/server.mjs:885-897` 在同一 `connectorId` 接入时先关闭旧 socket，再写入新 socket：

```js
connectors.get(connectorId)?.close(4000, 'replaced');
connectors.set(connectorId, ws);
```

旧 socket 的 close 处理在 `relay/server.mjs:942-952` 虽然用 `connectors.get(connectorId) === ws` 保护了 Map 删除，却没有用同一保护包住设备和发布表清理：

```js
for (const [deviceId, entry] of [...devices]) {
  if (entry.connectorId === connectorId) devices.delete(deviceId);
}
```

### 复现

两个同 `connectorId` 的真实 WS 连接，A 发布设备后 B 替换 A：

```text
before: connectors=1, devices=1
after replacement: connectors=1, devices=0
```

### 修复

在 close 回调开头判断 `const isCurrent = connectors.get(connectorId) === ws`；只有当前 socket 才能删除 connector、设备路由、发布表和所属流。旧 socket 被 replacement 时只能记录关闭。新增回归：B 发布设备后 A close，设备路由和 cookie 请求仍归 B。

## P0-2：连接器断开会误杀其他连接器的 HTTP 流

**影响：多连接器场景下 A 断开，B 的挂起 HTTP 请求收到 502。**

`relay/server.mjs:784` 保存 stream 时写入的是 `routeDeviceId`，不是真实 connectorId：

```js
streams.set(streamId, { res, connectorId: routeDeviceId, resourceUrl: req.url ?? '/' });
```

断开清理 `relay/server.mjs:954-965` 使用：

```js
const isThisConnector = (stream.connectorId === connectorId) || (stream.res !== undefined);
```

所有 HTTP stream 都有 `res`，因此条件恒为真。

### 复现

双连接器 A/B 分别发布 `devA/devB`，让 B 请求挂起后关闭 A：

```text
B got stream <stream-id>
B response after A close 502 connector disconnected
```

### 修复

路由阶段保存 `connectorIdOf(connector)` 或绑定 connector socket/generation；清理只匹配真实归属，删除 `|| stream.res !== undefined`。补双连接器挂起请求回归。

## P1-1：已发响应头后清理再次 writeHead

`relay/server.mjs:985-999` 收到 `http-res-head` 后已执行 `res.writeHead()`，但 stream 直到 final body 仍在 Map。连接器断开时 `relay.server.mjs:960-963` 又无条件 `res.writeHead(502)`，可能触发 `ERR_HTTP_HEADERS_SENT`，中断清理并让请求挂起。

**修复**：增加 `headersSent/settled` 状态；headers 已发送时只 destroy/end，不再 writeHead；所有 close/error 清理必须幂等并放在 finally。

## P1-2：响应头后没有 body/final watchdog

中继的请求 watchdog 只在 `http-res-head` 到达时清除（`relay/server.mjs:985-999`）。如果连接器发了响应头后不再发 body 或漏 `final:true`，客户端 HTTP 和 `streams` 可永久等待。

**修复**：增加响应体 idle watchdog、最大响应时长和 final deadline；每次 body 重置 idle timer，超时发送 504/502 并删除 stream。

## P1-3：客户端断开后没有取消上游 fetch/SSE

`relay/server.mjs:760-766` 的 response close 只删 Map 和 timer，没有发送 cancel。Connector `#handleHttp`（`transport/relay-client.js:457-557`）没有每流 AbortController；`forwardRequest`（`proxy/reverse-proxy.js:123-129`）只使用固定 115s timeout。SSE 读取虽然读取 `stream.streamAbort?.signal`，但该字段没有建立。

**影响**：手机离开页面后，本机 fetch/SSE 仍可能跑约 115 秒；重连后旧请求还可能用新 socket 发送迟到响应。

**修复**：新增 `http-cancel`；中继 response close、手机 WS close 和 connector close 都传播取消；Connector 每流 AbortController，`fetch` 和 reader 使用同一 signal；校验 socket generation，拒绝旧流帧。

## P1-4：上传中止后可能重新登记 orphan stream

`relay/server.mjs:760-820` 中，response close 只删除 Map，没有设置 aborted；请求仍可继续接收 data/end，`end` 会重新 `streams.set` 并发送到 connector，但 timer 已清理。连接器不回应时 stream 可永久占用。

**修复**：实现 `open → receiving → dispatched → responded → aborted` 状态；监听 `req.aborted`、`res.close`，aborted 后 data/end 不再缓存或发送；必要时 destroy request；补上传中止测试。

## P1-5：发送失败只 break，请求会等 110 秒

`relay/server.mjs:812-820` 在发送 `http-body` 失败时只 `break`，没有清 timer、删 stream、结束 response 或发送 cancel。用户会看到长时间转圈，Map 和 body 资源继续占用至 watchdog。

**修复**：统一 `abortHttpStream()`，在 head/body 发送失败时立即删除、结束 502/503、向连接器发送 cancel、记录 drop reason。

## P1-6：loopback WS upgrade 无超时

`proxy/upgrade.js:76-145` 的 `http.request` 没有 upgrade deadline，也没有保存 request 供 close 时 destroy。宿主接受 TCP 但不返回 101 时 bridge 永久未 ready，`RelayConnector.#streams` 条目持续存在。

**修复**：默认 10s upgrade timeout；升级、response、error、close 都清 timer；fail/dispose 同时 destroy request 和 socket；增加“永不返回 101”的回归。

## P1-7：Connector 发送端无 bufferedAmount 上限

`transport/relay-client.js:149-164` 只判断 readyState 便 send，中继端的 `MAX_SOCKET_BUFFER_BYTES` 无法限制 Connector 本地发送缓存。慢公网或中继消费变慢时，桌面进程内存和延迟可能持续增长。

**修复**：Connector send 检查 bufferedAmount；达到阈值记录 `socket_buffer_full`，按数据帧/控制帧分别处理并断流；补慢收端 RSS 与 bufferedAmount 测试。

## P1-8：未认证临时 pair UUID WS 可造成并发资源耗尽

`relay/server.mjs:1216-1285` 对无 cookie、无 `d` 的每条手机 WS 生成唯一 `pair-UUID`。`MAX_PHONE_PER_DEVICE` 只按 ID 限制，600/min 只限制建立速率，没有全局/每 IP active socket 上限；单 connector fallback 让任意公网客户端可持续打开任意路径 WS。connector 不回 `ws-accept` 时也没有 handshake timeout。

**修复**：未认证连接使用独立低配额；增加每 IP、每 connector、全 relay active WS 上限；WS open/accept deadline；失败时删除 streams/devices、关闭 phone socket。

## P1-9：Connector hello-ack 无 watchdog

`transport/relay-client.js:208-212` onopen 只发 hello；重试只由 close/error 触发。如果 upgrade 成功但 hello-ack 丢失，或旧 relay 接受连接却不回 ack，TCP/WS 仍可能被 ping/pong 保活，Connector 永远保持 `connecting`，不会 retry。

**修复**：open 后启动 hello watchdog（如 10s）；收到 hello-ack 清 timer；超时 close/terminate 并进入指数退避；补“永不回 ack”测试。

## P1-10：下行背压预算未计入当前 payload

`relay/server.mjs:1035-1046` 只判断发送前 `phone.bufferedAmount > 8MiB`，没有计算 `bufferedAmount + payload.length`。合法帧本身可以接近 16MiB，因此空缓冲也能一次越过预算。

**修复**：按 `bufferedAmount + payload.length` 判定并处理 send 竞态；必要时将单帧上限与手机桥上限统一收窄。

## P1-11：响应体写入忽略 `res.write()` 背压

`relay/server.mjs:1001-1009` 对 HTTP response `res.write(chunk)` 返回值不作处理，没有暂停 Connector 读取或应用层反压，慢 HTTP 客户端会令 Node writable buffer 增长。

**修复**：检测 `res.write()` 返回值；维护每 response writable budget；超限暂停上游/关闭 stream，或增加明确的 ACK/credit 流控。

## P1-12：流读取异常被伪装成正常结束

`transport/relay-client.js:601-607` 捕获 reader 异常只记录日志，随后无条件发送 `http-res-body final:true`。SSE/loopback 中途断开时，手机会把截断流当成正常结束，无法触发正确恢复。

**修复**：异常发送显式 `http-error` 或非正常 close；只有 reader 正常 done 才发送 final；补 mid-stream error 回归。

## P1-13：Pair-Proof 在 owner 断线窗口存在路由旁路

`relay/server.mjs:945` 无条件删除 `publishedDevices`，但 `deviceOwners` 保留。`onPhoneSocket`（`relay/server.mjs:1244-1263`）只检查 `publishedDevices`，不检查 `deviceOwners`。

### 影响和精确攻击链

持 relay token 的 phantom connector 等 owner 断线后，可用未认证参数 `/api/remote.mux?d=<owned>&c=<attacker>` 建立临时映射，把 `devices[owned]` 改到 attacker。攻击者自己的 `ws-open` 不含 victim cookie；随后 victim 的 cookie-only HTTP/WS 请求会被路由到 attacker，`http-head/ws-open` 才携带 victim cookie/业务流量，形成 Pair-Proof 旁路。

现有 route-hijack 回归只覆盖 owner 在线、`publishedDevices` 仍存在的窗口。

**修复**：路由归属检查以 `deviceOwners` 为最终事实；owner 断线不删除密码学 owner；设备重新归属必须有合法 claim 或显式撤销/重配；补 owner 断线后 phantom connector 攻击回归。

## P2-1：PWA 模式不具备真正端到端加密

`transport/e2e.js` 目前只被测试引用，未接生产 carrier，且现有原语是裸 ECDH，未形成带设备认证的生产握手。`README.md:158-164` 和 `docs/安全加固落地记录.md:98-100` 已如实说明：中继 TLS 终止后可观察/篡改 PWA，6 位码不能抵御恶意中继改写配对页 JS。

**建议**：产品定位明确为“信任中继 TLS”；若需抵御恶意中继，先设计认证密钥交换，再接生产链路并补 MITM/降级测试。

## P2-2：unsafe relay token 会退回 URL，存在日志泄漏

`transport/relay-client.js:177-181` 和 `probeRelay:833-835`：如果令牌不匹配 `SAFE_TOKEN`，会写入 `/connector?...&token=`。包含 `+`、`/`、`=` 等字符的合法 token 可能进入 Caddy/代理 URI 日志。代码头部“token 不进 URL/日志”与该分支矛盾。

`relay/server.mjs:630-637` 也接受 `/metrics?token=`；README 公开该用法。query token 可能进入浏览器历史、Referer、访问日志。且 relay token 与 connector 鉴权复用，泄漏后可接管中继接入。

**修复**：禁止 token query fallback；只使用安全子协议或专门 header；metrics 使用独立只读 token，优先只接受 Authorization header。

## P2-3：中继并发资源预算不足

`relay/server.mjs:155-160` 的 8MiB request/body、8MiB phone buffer、64MiB Connector response 是单流上限；`streams` 没有全局数量上限。systemd `MemoryMax=512M` 超限时只是杀进程并重启。

**修复**：增加每 IP、每 connector、每 device 和全 relay active stream/累计 buffer 上限；超限 429/503；导出活动流、buffer 高水位、RSS 和 event-loop delay。

## P2-4：生产 per-request debug 日志过于频繁

`relay/server.mjs:664,704,801` 对每个请求用 `console.error` 输出 debug；健康探针也会产生日志。查询串虽已脱敏，但高流量下会增加 I/O、journal 体积和排障噪声。

**修复**：生产默认关闭 per-request debug；保留采样、限流、丢帧、错误和状态转移日志；配置 journal 限流和磁盘配额。

## P2-5：部署脚本会明文打印 relay token

`relay/deploy/install.sh:264-293` 将 TOKEN 打印在安装汇总和后续命令中。Caddy restart 也可能造成同机其他站点短暂中断（`install.sh:219-226`）。当前未见部署包签名校验。

**修复**：只输出 token 指纹和从 0600 文件读取的命令；优先 Caddy 原子 reload；为部署包做签名/可信来源验证和版本回滚。

## 五、性能、速度、同步与稳定性

### 5.1 连接速度

Connector 重连退避为 `1s → 30s` 加最多 500ms 抖动（`transport/relay-client.js:268-279`），可防止重连风暴；中继 connector keepalive 默认 30s，phone keepalive 默认 60s。

但半开连接最多要等待 keepalive 周期，且没有业务级健康 ACK。应采集：

- `connect_start → socket_open → hello_ack → first_routeable_request` p50/p95/p99；
- DNS/TLS/upgrade/hello 各阶段耗时；
- 重连原因和退避次数；
- 设备发布完成耗时。

### 5.2 读取/首屏速度

资源指纹 immutable、gzip、二进制承载和移动皮肤注入是有效优化。风险在于：

- 中继 request body 先全量聚合（`relay/server.mjs:768-784`）。
- 非 SSE 响应先 `arrayBuffer()`（`proxy/reverse-proxy.js:145-175`）。
- 64MiB 响应上限在完整读取后才检查，拒绝前已经发生内存放大。
- 二进制封装不必然降低本机 CPU；本次 512KiB×100 编码基线 JSON 约 17.2ms，binary 约 45.0ms。真实收益须用端到端网络/TTFB/CPU 共同测量。

### 5.3 同步速度和一致性

正常在线且未触发背压时，WS 有序传递和现有分片测试证据较好。断线/后台/换网场景没有 ACK、seq、resume 和 replay：当前行为是断桥后重新连接、重新拉取上层状态，不能宣称实时流无损。

### 5.4 重连恢复

已实现指数退避、Blob 兼容、入站串行、设备发布自愈、Pair-Proof owner 重放和 kill switch 强制关闭；但仍受 replacement 清理竞态、跨 connector 清理误杀、in-flight fetch 不取消、无 generation/seq 影响。

### 5.5 长期运行

`streams` 可能因客户端 abort、发送失败、升级黑洞或缺 final 持续保留；单流限制不等于并发预算；Connector 发送端无 bufferedAmount 上限；生产 debug 日志可能产生高 I/O。长跑前必须做 RSS、fd、活动 stream 数、buffer 高水位和 event-loop delay 监控。

## 八、建议验收标准

| 类别 | 关门条件 |
|---|---|
| 路由 | 同 ID 替换 100 次，设备路由不丢；旧 close 不影响新连接 |
| 多连接器 | A/B 各 100 条挂起请求，随机断 A，B 请求 100% 不被误杀 |
| 生命周期 | 客户端断开后 1 秒内 upstream fetch/reader/relay stream 全部释放 |
| 发送失败 | 1 秒内返回可读 502/503，不等待 110 秒 |
| WS upgrade | 宿主不回 101 时 10 秒内释放句柄；重复 1000 次 RSS 不单调增长 |
| 内存 | 受限并发压测下 RSS 有上限，活动流、buffer bytes 和 event-loop delay 可观测 |
| 弱网 | 4G/3G/离线 30 秒/切后台恢复后，统计快照恢复、丢帧和重连耗时 |
| 门禁 | `npm test` 和 `npm run verify` 在干净临时环境退出码均为 0 |

## 九、最终结论

项目的正常路径和安全加固基础已经达到较好的内部测试水平；影响公网长期稳定性的主要问题集中在**连接归属、异常生命周期、背压和断线恢复**。

在 P0/P1 修复前，建议产品承诺限定为：

> 正常网络下可用；连接断开后尝试指数退避重连；实时流在断线期间可能需要重新拉取快照。

不要承诺“断线无损恢复”“所有在途请求立即取消”“重连后状态必然无缝续传”。完成 P0/P1、弱网和容量实测后，再重新评估公网长期运行等级。
