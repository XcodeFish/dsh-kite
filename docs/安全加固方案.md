## 0. 根因：判定用的字符串 ≠ 发送用的字符串

所有 Critical 级问题来自同一个结构缺陷：**请求目标被解析了两次，判定看第一次，发送用第二次。**

```text
手机请求目标 raw ──► policy.decide(raw) + safeProxyPath(raw)     ← 判定看的是这个
                 │
                 └──► new URL(raw, base)  ──► 归一化 / authority 切换 ──► fetch 真正请求的东西
```

两次解析之间的映射差异，就是全部绕过面：

| 差异 | 例子 | 后果 |
|---|---|---|
| 点段折叠 | `/./kite/api/relay`、`/x/../kite/api/relay` | 保留路径 `/kite` 判定失效 → 管理面从手机可达 |
| authority 切换 | `//attacker.tld/x` | 请求发出机器，且附带回环凭据（SSRF + 凭据外泄） |
| 编码点段 | `/%2e/kite/...` | URL 把 `%2e` 当点段折叠，判定看不见 |
| 同族规则 | `/y/../api/session/uploadFileBinary` 等 | 上传/HMR/市场/终端/会话预设锁定全部失效 |

**因此修法只有一条正确路线：只解析一次，把同一个解析结果同时交给「判定」和「发送」。**
任何"在 `safeProxyPath` 里多加几条正则"的做法都是在枚举攻击者的写法，属于黑名单思维，必然有下一个漏网写法。

## 1. P0-1 规范化收口（一处函数，三个调用点）

### 改什么

`policy/methods.js`：用 `canonicalizeTarget()` 取代 `safeProxyPath()` 的判定职责（`safeProxyPath` 保留为一行包装，现有断言不动）。

```js
// policy/methods.js
/** 规范化基准 origin：固定且不可路由，只用来让 URL 解析器做归一化。 */
const CANON_ORIGIN = 'http://kite.invalid';

/**
 * 唯一入口：请求目标字符串 → origin-form 的 { pathname, search, key }。
 * ★ 下游（策略判定 / 审计 / 出站 URL 组装）必须使用同一个返回值，禁止再解析原始串。
 * 返回 null = 直接 400。
 */
export function canonicalizeTarget(rawTarget, limit = 8192) {
  if (typeof rawTarget !== 'string' || rawTarget.length === 0 || rawTarget.length > limit) return null;
  // 必须 origin-form：恰好一个前导 '/'（'//' 是 protocol-relative，会切 authority）
  if (rawTarget[0] !== '/' || rawTarget[1] === '/') return null;
  if (rawTarget.includes(' ') || rawTarget.includes('\\') || rawTarget.includes('#')) return null;
  // eslint-disable-next-line no-control-regex
  if (/[\u0000-\u001f\u007f]/.test(rawTarget)) return null;
  let url;
  try {
    url = new URL(rawTarget, CANON_ORIGIN);
  } catch {
    return null;
  }
  // authority 被改写（//host、http://host、\\host 之类的变体）→ 一律拒
  if (url.origin !== CANON_ORIGIN) return null;
  // pathname 里出现百分号编码的 / \ . 与控制字符：URL 只折叠 %2e，%2f/%5c 会原样透给宿主，
  // 宿主若再做一次 decode 就又是一次「判定/发送」差异。这三个字节在 DSH 的 pathname 里无合法用途。
  if (/%(2f|5c|2e|0[0-9a-f]|1[0-9a-f]|7f)/i.test(url.pathname)) return null;
  return { pathname: url.pathname, search: url.search, key: `${url.pathname}${url.search}` };
}

/** 兼容保留：现有测试与调用方只关心「是否可代理」。 */
export function safeProxyPath(path, limit = 8192) {
  return canonicalizeTarget(path, limit) !== null;
}
```

`Policy.decide()` 里的保留路径判定改为对**规范化结果**生效（`path` 参数由调用方传入 `target.key`，判定逻辑本身不用改；改动集中在调用方）：

```js
// policy/methods.js 第 ⑥ 条保持原样即可 —— 它现在收到的是规范化后的 path
if (path === '/kite' || path.startsWith('/kite/')) return deny(404, 'reserved');
```

### 为什么

1. **为什么用"先解析再判定"，而不是"判定后再解析"？** 因为解析是攻击者可控的语义归一化。把解析结果作为唯一的真值（single source of truth），映射差异就不存在了；反之永远要回答"还有没有别的写法能绕过"。
2. **为什么把 `%2e/%2f/%5c` 直接拒掉？** 这是唯一一处"判定与宿主可能再次不一致"的残留面（宿主路由若做一次 decode）。这些编码在 DSH 的 pathname 里没有合法用途，拒掉零功能损失；只查 pathname，不动 query（query 里 `%2F` 是合法的，例如路径参数）。
3. **为什么保留 `safeProxyPath`？** `test/policy.test.mjs:98-110` 已有 6 条断言依赖它，保留成一行包装可让本次修复的 diff 只碰逻辑、不碰测试语义，降低回归面。
4. **为什么不选"在 relay 侧归一化 `req.url`"？** relay 是不可信组件（README 自己这么定的），把安全归一化放在不可信侧等于把锁挂在门外；connector 侧必须是唯一判据。

+    //   在 loopback origin 上贴 pathname/search —— URL 的 pathname setter 不碰 host/port。

+    url.search = target.search;

+      // 结构上不可达；留作不变式断言，改坏了会立刻炸。
+      return respond(500, { 'content-type': 'application/json' }, json({ error: 'proxy/origin-violation' }));

### 为什么

1. **纵深防御**：即使 P0-1 未来被改坏，出站目标也**结构上不可能**离开 loopback origin —— 这类"改坏了就立刻报错"的不变式，比注释和 code review 可靠。
2. **为什么不用「assert hostname === 127.0.0.1」？** 那种检查依赖字符串比较，容易在 IPv6/别名（`localhost`、`[::1]`、`127.1`）上漏；比较 origin 是完整的语义比较。
3. **为什么 `url.pathname = ...` 是安全的？** pathname setter 只跑 path 解析（再折叠一次点段，此时已无点段可折），不会触碰 host/port/scheme —— 这正是我们要消除的那一类操作。

## 4. P0-4 管理面纵深防御：来源标记头

即使 P0-1~P0-3 修好，管理面仍依赖"宿主认为这条回环请求已认证"这一条链。但连接器**必然**以已认证身份访问宿主，于是"回环 = 已认证 = 可信"在代理场景下失效。加一条手机写不进去的来源标记。

### 改什么

`proxy/reverse-proxy.js`：

```js
// 进程级随机值：即使将来白名单误放行了同名头，手机也猜不到值。
export const VIA_HEADER = 'x-kite-via-connector';
export function rebuildRequestHeaders(logicalHeaders, cookie, viaValue) {
  const headers = { cookie, [VIA_HEADER]: viaValue };
  for (const [name, value] of Object.entries(logicalHeaders ?? {})) { /* 白名单不变 */ }
  return headers;
}
```

`admin/panel.js` `adminAuth()` 开头：

```js
function adminAuth(req, url, deps) {
  // ★ 经代理来的请求永远不许进管理面。标记头由连接器在【按白名单重建之后】无条件写入，
  //   手机无法伪造、也无法阻止（它的一切头都被丢弃）。
  if (req.headers[VIA_HEADER] === deps.viaValue) {
    return { ok: false, status: 403, body: '管理面不接受经远程代理到达的请求。请在桌面端本机打开。' };
  }
  ... 原有三轨 ...
}
```

`index.js`：boot 时 `const viaValue = randomUUID()`，同时传给 `RelayConnector`（转发时写入）与 `createAdminHandler`（校验）。

### 为什么

1. **为什么不是"直接删掉 adminAuth 的宿主会话轨（track 3）"？** track 3 是"在浏览器打开 DSH"这条正当入口的依赖，删掉会破坏功能。标记头只否定"经代理来的"，把两个入口干净地分开。
2. **为什么用随机值而不是固定 `1`？** 固定值依赖"手机一个头都进不来"这一条不变式；随机值让这条不变式被破坏时仍然安全（fail-safe 而不是 fail-open）。
3. **为什么标记头是可信的？** 因为它在 `rebuildRequestHeaders` 里、白名单过滤**之后**写入 —— 数据流向决定了手机无法影响它。这是"用结构保证"而不是"用检查保证"。

`identity/pairing.js:95` 算出 `code = f(设备公钥, 连接器公钥)`，然后：

- PWA 路径：`admin/panel.js:393` 把 code 放在 JSON 里回给手机；
- 手机侧 `admin/panel.js:467` 只是 `textContent = doneData.code` —— **手机从不自己计算**（`admin/` 里没有任何 `crypto.subtle.digest`）。

于是"两端比对"退化成"连接器跟自己对账"：恶意中继把 `pubKey` 换成自己的，连接器回什么它就转发什么，两端数字当然一致。README 的"防中继抢配"没有落地。

### 第一层修复（便宜、必须做）：手机本地计算

```diff
# admin/panel.js —— 配对链接带上连接器公钥（公钥，放 URL 安全）
-  ? `${base}/kite/pair?token=${token}&name=…&c=${deps.fingerprint}`
+  ? `${base}/kite/pair?token=${token}&name=…&c=${deps.fingerprint}&pk=${deps.keys.ed25519.publicB64u}`

# admin/panel.js —— 手机侧自己算，不再显示服务端给的数
-    $('code').textContent = doneData.code;
+    const digest = await crypto.subtle.digest('SHA-256',
+      new TextEncoder().encode(pubB64 + '|' + new URLSearchParams(location.search).get('pk')));
+    const n = ((digest[0] << 16) | (digest[1] << 8) | digest[2]) % 1000000;
+    $('code').textContent = String(n).padStart(6, '0');
```

（`pk` 来自用户扫码时地址栏里的 URL；`|` 分隔与字节序必须与 `identity/pairing.js:23-27` 完全一致。）

### 第二层：把话说准（同样的重要）

**必须承认的边界**：配对页的 JS 也是经中继下发的。一个能改写页面的中继，同样能改写这段本地计算 —— 所以"6 位校验码"从原理上**无法**对抗"能改写客户端的中继"。它能挡住的是：

- 只做字段替换/竞速的"被动+转发"式中继（第一层修复后会被两端数字不一致暴露）；
- 日志/内存里读到配对令牌后抢配的第三方。

**真正对抗恶意中继只有两条路**（两条都已在 ADR 里，只是没交付）：

| 路线 | 为什么有效 | 成本 |
|---|---|---|
| thin client / sealed 模式：客户端不从中继加载（应用商店或本机安装，受 OS 信任链保护）+ X25519 认证密钥协商 | 中继无法改写它加载不到的代码；密钥协商必须认证（**当前 `transport/e2e.js` 是裸 ECDH，没有认证，且是死代码，不能算既有防线**） | 高（新客户端） |
| 局域网/Tailscale 直连路径（README §5 已列）：配对不走中继 | 中继不在信任链上 | 低（文档 + 引导即可） |

**因此 P1-3 的交付物是两件事**：(1) 上一层本地计算；(2) 把 README §7 的"防中继作恶抢配"改成如实的边界描述，并把"中继被劫持时请用 Tailscale/局域网路径重配"写进排障表。

### 为什么不做"面板上点击允许"

我评估过"由人在 Mac 面板上点允许"，结论是**它不成立**：面板展示的设备标识对人不具可读性，而任何"手机屏幕上显示的数字"都不可信（手机 JS 由中继下发）。让可信屏幕去核对不可信屏幕，不构成安全边界；只会制造"我们做了二次确认"的错觉。

## 8. P1-4 引导令牌：时长与投放面

### 改什么

```diff
# admin/panel.js
-const BOOTSTRAP_TTL_MS = 24 * 3600 * 1000;
+const BOOTSTRAP_TTL_MS = 10 * 60 * 1000;   // 与注释/README 一致

-        const token = keysRef.signPayload({ kind: 'kite-bootstrap', iat: now, exp: now + 24 * 3600 * 1000 });
+        const token = keysRef.signPayload({ kind: 'kite-bootstrap', iat: now, exp: now + 10 * 60 * 1000 });
```

并且**不要把这个令牌写进会下发给远程设备的 HTML**：`menu-entry.js` 的注入面是 DSH 首页，而首页同样经代理下发给手机。改为注入脚本在需要时调 `/kite/api/entry` 现取（该端点本就免认证、且修复后手机不可达）。

```diff
# admin/menu-entry.js
-    { kind: 'global', name: '__DSH_KITE_AUTH__', value: { url: authedUrl } },
+    { kind: 'global', name: '__DSH_KITE_AUTH__', value: { url: '/kite' } },   // 令牌改为按需现取
```

```js
// admin/panel-client.js：面板打开时现取（父上下文 fetch 自带宿主 cookie）
const entry = await fetch('/kite/api/entry', { credentials: 'same-origin' }).then(r => r.json()).catch(() => null);
const panelUrl = entry?.url || __DSH_KITE_AUTH__.url;
```

### 为什么

1. **文档说 10 分钟、代码是 24 小时**，差 144 倍不是笔误级别：泄漏面（浏览历史、截图、录屏、会话分享）实际有效期完全不同。安全参数以代码为准、以文档为准都行，但不能不一致。
2. **令牌不该出现在任何"会离开本机"的字节流里**。`webserver/index-inject` 的产物是顶页 HTML，而顶页 HTML 正是手机要加载的东西 —— 把管理面凭据放进"必然发给不可信端"的载荷里，等于把防线建在"手机不会读自己的 HTML"这个假定上。

## 10. 回归测试：为什么 146 项没抓到，以及该加什么

> **落地后记**：本节要求的测试已实现为 `test/canonicalize.test.mjs`（10 项，按不变式而非字符串枚举）+ `test/relay-hardening.test.mjs`（中继侧 6 项），并补了本节未预见的两个用例：双编码 `%25` 残留、校验码手机侧算法与 `identity/pairing.js` 的跨端一致性。测试基线：撰写时 146/147，落地后 **183 项全绿**。

**没抓到的原因**：现有断言全部使用**规范写法**。`test/policy.test.mjs:87` 只测 `/kite/api/status`，`:98` 只测 `http://evil/x` —— 一个"同一语义的另一种写法"的维度完全缺失。

**要加的测试（按不变式而不是按用例写）**：

```js
// test/canonicalize.test.mjs
const HOSTILE = [
  '/./kite/api/status', '/x/../kite/api/relay', '/%2e/kite/api/status',
  '//evil.example/x', '///evil.example/x', '/kite%2Fapi%2Fstatus',
  '/y/../api/session/uploadFileBinary', '/z/../plugins/events', '/q/../api/community-market/list'
];
// ① 规范化不变式：要么拒，要么规范化结果不得命中任何受限前缀
// ② 出站一致性：stub fetch 捕获 URL，断言 url.pathname === policy 收到的 pathname
// ③ WS 同一道门：ws-open 帧带上述路径 → 必得 ws-close(4400/4403)
// ④ 管理面隔离：带 x-kite-via-connector 的请求 → 403 / 不进 adminAuth
// ⑤ 回归护栏：kill switch on 后 forwardRequest 立即 503
```

其中 ② 是最有价值的一条：它把"判定与发送必须同源"从注释变成可执行断言 —— 这类缺陷的本质是两条代码路径，而不是某个具体字符串。
