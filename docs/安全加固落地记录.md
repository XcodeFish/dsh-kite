## 三、收尾复核中发现并补上的两处（原报告与方案都未列）

### 3.1 `/kite/api/entry` 曾绕过来源隔离

**`/kite/api/entry` 曾绕过来源隔离**：该端点为了避开「要令牌才能拿令牌」死锁而设计成免认证（在 `adminAuth` 之前 `return`），因此它是整条管理面上**唯一**不受 ⓪ 轨保护的地方 —— 一旦代理侧策略被绕过（或未来又出现新的写法绕过），攻击者可直接白拿 10 分钟引导令牌，进而进管理面。

已在 handler 最前面加来源隔离（与 `adminAuth` 用同一判定与审计），并进回归：带标记头 → 403 且响应体绝不含 `kite_token`；本机访问仍正常签发（死锁修复不回退）。这类「免认证旁路」是路径收口类修复的典型遗漏点，值得在其它项目复用同一条检查：**收口必须覆盖所有入口，包括刻意免认证的那个**。

### 3.2 两个 socket 泄漏（真实缺陷，非仅测试问题）

验收阶段发现 `npm test` 会出现「183 项全过但不退出」。逐层定位（去掉新增测试文件 → 干净退出；单跑定位到具体文件 → 句柄快照）后确认是**生产代码的两处优雅关闭没有兜底**，测试只是把它显形：

| 位置 | 旧行为 | 后果 | 修法 |
|---|---|---|---|
| `proxy/upgrade.js` `dispose()` | 只 `socket.end()`（发 FIN 等对端） | 宿主侧不回收就永久 CLOSE_WAIT —— **每条被关闭的 WS 隧道泄漏一个僵尸 socket**，长跑必积压 | 1s 宽限后 `destroy()`（定时器 `unref`） |
| `transport/relay-client.js` `#closeSocket()` | 只 `ws.close()`（等对端 close 握手） | 中继卡死时 kill switch 表现为「已停用但连接还在」 | 1s 宽限后 `terminate()`（定时器 `unref`） |

另修测试侧清理：`withProxyHarness.close()` 加 `closeAllConnections()`（fetch 的 keep-alive 连接不随 `server.close()` 断开），WS 用例统一走 `hardCleanup()`。

**验证**：纯 `npm test`（不带任何 flag）→ **183/183、EXIT=0、零残留进程**。因此 `--test-force-exit` 只是定位期的临时手段，不应成为常规做法（`package.json` 的 test 脚本保持原样）。

## 四、与原方案的偏离与修正（4 处）

1. **§1 的 `%25` 残留已补**：原方案只拒 `%2e/%2f/%5c`，双编码 `/%252e/kite/...` 会原样透给宿主（宿主若再解码一次就重新出现点段）。现增加「含 `%25` 时额外解码一次，若解出结构编码即拒」，并进恶意矩阵。
2. **§3 的签名变更需同批改测试**：`openLoopbackBridge` 入参由 `path` 改为 `{pathname, search}`，3 处既有测试调用点必须同批更新，否则「现有测试保持全绿」不成立（已一并更新）。同时把入参校验做成**抛错而非 `?? '/'` 兜底** —— 旧调用方会立刻暴露，而不是静默去请求宿主根路径。
3. **§6 限流阈值按部署形态分桶**：以 60/min 为全局桶会打断 PWA 首屏（一次 50~60 个模块请求，且经 Caddy 后所有手机共享回环 IP）。落地为三桶 + **仅回环来源采信 XFF** 还原真实客户端。
4. **§9 P2#7 移除宿主 launchToken 轨**：这条会影响 `test/relay-config.e2e.test.mjs`（它原先靠 launchToken 认证）。已同步改为经 `/kite/api/entry` 取插件自签令牌 —— 与面板真实入口同源。

## 六、残余风险（如实清单）

1. **能改写配对页 JS 的中继仍可绕过 6 位校验码**：本地计算挡得住「字段替换/竞速」与「读到令牌后抢配」，挡不住改写客户端。真解只有 thin-client sealed（`transport/e2e.js` 目前仅被测试引用、未接生产链路，且是裸 ECDH 无认证）或局域网/Tailscale 直连。README §7 已如实写明。
2. **XFF 分桶的前提**：中继前只有 Caddy 一层反代（Caddy 未配 `trusted_proxies` 时会覆写 XFF）。若将来前面再加 CDN/LB，需改为取最后一个条目或在 Caddy 侧 `header_up`。代码注释已标注。
3. **`device-claim` 写入 owners 表未设上限**：`MAX_DEVICES` 只约束 `devices` 帧（按原方案范围）。
4. **响应体先缓冲后判上限**：`forwardRequest` 在 `arrayBuffer()` 之后才判 64 MiB，内存放大发生在拒绝之前；中继侧响应背压只覆盖一半。
5. **中继开放模式仍可被误配**：fail-closed 已把「静默开放」变成「拒绝启动」，但显式 `ALLOW_OPEN=1` 上生产仍无人拦（只能靠每次启动的刺眼警告 + 部署文档）。

## 附：2026-10-03 GUI「Failed to load plugins」事件定性与处置

**现象**：应用启动后首屏出现 HARNESS 引导失败浮层，`web boot: 1 entry did not activate`，
`@deepseek-ai/dsh-client-ui-settings-account: import failed: client-modules: could not load … plugins/??…`（其后是整串 batch URL）。

**定性（源码级，app 0.2.0-rc.2）**：本插件无责，属宿主侧的**陈旧引导图瞬态**：

1. 桌面壳在 Host 就绪时**一次性捕获** boot 注入（`ipcMain.handle(DESKTOP_IPC.boot)` 每次页面加载都返回同一份捕获值）。
2. Host 的 client-modules 图在捕获之后仍可能重排（`dsh-client-hmr` 装载 watch 后对 baseline 漂移的 bundle 调 `rebuilt(id)`、插件激活晚 flush 等）。
3. 首屏用旧图启动：旧 batch URL 在 Host 的 responses 表里最多保留一个世代（`previousBatchResponses`），超过即 404；随后每个成员回退各自的单包 URL `plugins/??<id>/client.js&rev=<旧 rev>`——rev 未变的成员仍命中 responses 表正常注册；**rev 变了的成员（本例 settings-account，5.2MB 大包，曾经历 Jet-Hub 硬链接同步触达）单包 URL 404** → `could not load`，恰好一个条目失败。
4. 自愈回路：`client-hmr` 客户端半连上 `/plugins/events` SSE 后会收到**当前图**帧，`entries.sync()` 重试失败条目，浮层随即消失（或一次刷新恢复）。这就是「截图时失败、现在 GUI 正常」的原因。

**处置**：无需代码修改；确认重载后 GUI 恢复、`node --test test/*.test.mjs` 191 全过 + 全套 e2e 通过。
若宿主后续要根治，方向是 `DESKTOP_IPC.boot` 每次返回时实时调 `collectIndexInjections()`（或 Host 把当前图随 ready 后经 SSE 首帧兜底），避免任何 reload 复用启动时捕获的旧图。
